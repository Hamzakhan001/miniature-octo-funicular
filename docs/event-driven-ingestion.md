# Event-Driven Ingestion Design

This project now follows a cloud-shaped control plane for document ingestion:

`Frontend -> upload session API -> object storage -> queue event -> Lambda or Fargate processor`

## Why this design

- The API only handles control-plane work such as validating upload requests, generating object keys, and tracking status.
- Raw files live in object storage first. That keeps uploads durable and decouples them from downstream processing speed.
- Queue events carry metadata only, not file bytes. That reduces coupling and makes retries safer.
- The first processing decision is event-driven. Lightweight files stay on the Lambda path. Heavier files are routed to Fargate.

## Components

### `IngestionOrchestrator`

The orchestrator is the control-plane entrypoint. It:

- validates file extension and file size
- creates a job record
- chooses the processing target with `ProcessingRouter`
- asks the configured storage backend for an upload target
- publishes an ingestion event after a server-mediated upload

### `StorageService`

This abstracts where raw files land.

- `LocalStorageService` is the development fallback
- `S3StorageService` is the cloud path

The orchestrator depends on the abstraction, not directly on S3.

### `QueuePublisher`

This abstracts how ingestion events are emitted.

- `MemoryQueuePublisher` is a non-scaling development fallback
- `SQSQueuePublisher` is the cloud path

The queue only carries metadata such as `job_id`, `object_key`, `file_size_bytes`, and the chosen processing target.

### `SQLiteJobRepository`

This tracks user-visible job state. In production, the same boundary can be replaced with DynamoDB.

### `ProcessingRouter`

This is the routing policy:

- small, Lambda-friendly files stay on the Lambda path
- larger or heavier file types are offloaded to Fargate

## Security practices baked into this design

- object keys are generated server-side
- filenames are sanitized before they become storage keys
- file bytes are never placed on the queue
- the API validates file extension and max size before creating a job
- direct upload URLs are generated by the backend rather than by the browser
- status tracking is separate from the queue itself

## Recommended AWS production flow

1. Frontend calls `POST /api/v1/ingest/uploads/create`
2. Backend returns a presigned S3 URL plus a `job_id`
3. Frontend uploads directly to S3
4. S3 emits an object-created event to SQS
5. Lambda consumes the SQS message
6. Lambda decides:
   - process inline for lightweight files
   - dispatch a one-off Fargate task for heavier files
7. Processor updates the job record and writes vectors downstream

## Why Lambda first, then Fargate

Lambda is the best first event-driven hop because:

- there is no long-running poller to manage
- cost stays low for common lightweight files
- it is a natural place to run the routing policy

Fargate remains part of the design because:

- larger PDFs, DOCX, or CPU-heavy parsing may outgrow Lambda
- heavier dependencies fit better in a container
- tasks can start on demand rather than staying alive and polling
